# Daily Ledger

A personal planning workspace with a screenshot-led black dashboard. Next.js App Router/TypeScript frontend, GSAP, Tailwind, Radix/shadcn-style components, Lucide, Recharts, TanStack Query and React Hook Form/Zod. The separate Express API uses PostgreSQL/Prisma, Passport Google OAuth plus email/password authentication, PostgreSQL sessions, and Resend. No Supabase.

## Run the frontend immediately

Requires Node 22.12+ (Node 24 LTS recommended) and npm. From the repository root:

```sh
npm ci
npm run dev
```

Open http://localhost:3000. Default **demo mode** is explicitly labeled, uses a September 30, 2026 demo clock, and stores edits in the browser key `daily-ledger-demo-v1`. It never authenticates a demo identity or mixes demo data into signed-in records. September totals are derived from shared records: $4,000 income, $1,280 expenses, $2,720 savings, 18/24 due tasks. The habit rate is calculated from actual scheduled completions, rather than copying an unsupported percentage from the reference.

All sidebar pages work. Quick add, record editing/deletion, task/grocery/habit completion, budgets, recurring definitions, workout logs, meal planning, goals/milestones, filters, global search, unread notifications, preferences, CSV and JSON exports use the same adapter. PDF is generated by the connected API. The personal workspace selector explains the single-workspace model.

GSAP uses scoped `useGSAP` contexts with cleanup and media queries. Recharts native animation is disabled on dashboard charts to prevent double animation. Skeletons represent actual initial query pending states; no artificial delays. Reduced motion disables entrances/count-ups/shimmer. Demo records are not production payments or Google sessions.

Feature pages share the refined login/signup visual language, with compact typography, dark gradient surfaces, consistent controls, and useful summaries. Finance includes remaining budget, spending averages, category drill-down, paginated transactions, and mobile transaction rows. Tasks/habits and fitness have balanced desktop columns; meals use calendar weeks, and goals show remaining progress/milestones. Money forms use normal decimal amounts (for example `12.50`), and convert exactly to stored cents; relationship selectors show names instead of IDs. The supplied logo is used across the dashboard and auth pages. See [UX research and implemented decisions](UX-RESEARCH.md).

## Local API and PostgreSQL

```sh
docker compose up -d
```

Copy `apps/api/.env.example` to `apps/api/.env`, and `apps/web/.env.example` to `apps/web/.env.local`. Generate a session secret with `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` and put it **only** in the API env. Set `NEXT_PUBLIC_DATA_MODE=api` in the web env and restart Next.

```sh
npm run db:generate
npm run db:migrate
npm run dev:api
# In another terminal:
npm run dev
```

The API runs on port 4000. The Next proxy `/backend` forwards to it; browser requests remain same-origin on port 3000. Local Google callback: `http://localhost:3000/backend/auth/google/callback`. Email signup/login works with the local database, without Google credentials. Open `/signup` or `/login`. Signup asks for full name, email, and password; your display name can be changed in Settings. Password requirements (12–128 characters and letters/numbers/symbols) are shared by the UI and backend. There is no fake production login. A successful session switches the frontend to real account records even in the default demo build. Google sign-in clearly reports missing configuration.

Database seeds are opt-in, local-only, and never run on startup or deployment. After signing in to a local account, set `DEMO_GOOGLE_ID` to that account's stable Google provider ID and run `npm run db:seed -w @ledger/api`. Never use real production credentials with local seed commands. Seeding is idempotent and refuses `NODE_ENV=production`.

For disposable Windows verification without Docker, install `@embedded-postgres/windows-x64` under `artifacts/pg-test` using `npm install --prefix artifacts/pg-test @embedded-postgres/windows-x64`, then run `node scripts/local-postgres.mjs`. It binds only to `127.0.0.1:5439` with local trust authentication and stores test files in ignored `artifacts/`. Use `postgresql://ledger@127.0.0.1:5439/postgres`, apply the migrations, and stop it with `node scripts/local-postgres.mjs stop`. This helper is for a disposable local test database only.

## Login, signup and password recovery

`/login` and `/signup` share the screenshot-inspired black layout, silver SVG folded corners, restrained GSAP entrance, Google button, and email/password fields. Signup has a full-name field and live password requirement indicators. `/forgot-password`, `/reset-password`, `/terms`, and `/privacy` are real routes. Authenticated users are redirected to validated internal destinations. External/encoded redirect targets and auth-page loops are rejected.

Password hashes use native salted scrypt. Email sessions rotate on authentication; reset links expire after one hour, are single-use, and invalidate existing sessions. Reset delivery requires `RESEND_API_KEY`, verified `EMAIL_FROM`, and the scheduled worker with the **same `SESSION_SECRET`** as the API. Without delivery configuration the UI reports that reset email is unconfigured. No successful email delivery is simulated. Email verification and identity linking are not implemented; use the original sign-in method for an existing account. Configure and verify email ownership before relying on email as a verified identity.

## Google OAuth

1. In Google Cloud Console create a project, configure Google Auth Platform branding/audience and an OAuth web application client. During testing add your account as a test user.
2. For local development authorize origin `http://localhost:3000` and the exact redirect URI `http://localhost:3000/backend/auth/google/callback`.
3. Put client ID, client secret, and callback URL in the **API** environment. Requested scopes are only `profile` and `email`.
4. Production: authorize origin `https://app.dailyledger.store` and callback `https://api.dailyledger.store/auth/google/callback`. These are proposed domains; DNS is not provisioned by this repository.
5. Set `FRONTEND_ORIGIN` to the exact browser origin. Login uses provider ID, OAuth state validation, session rotation, HttpOnly host-only cookies, and a per-session CSRF token. Logout destroys the persisted session.

## Deploy frontend to Vercel

- Import this repository; set root directory to `apps/web`. Enable access to files outside the root for workspace dependencies. Use the npm lockfile at the workspace root.
- Build command: `npm run build -w @ledger/web` from repository root (or `npm run build` from the web directory). Install command: `npm ci` from workspace root.
- Set `NEXT_PUBLIC_DATA_MODE=api`, `NEXT_PUBLIC_API_URL=https://api.dailyledger.store`, and `API_INTERNAL_URL=https://api.dailyledger.store`. Only public URLs/mode belong in public env vars.
- Add `app.dailyledger.store` as a Vercel domain and configure the DNS records Vercel provides.
- Alternatively deploy the demo with `NEXT_PUBLIC_DATA_MODE=demo`; it must remain labeled.

## Deploy Express and PostgreSQL to Railway

- Create a project with PostgreSQL and a repository-backed API service. Use repository root as service root so shared contracts and lockfile are available.
- Install/build: `npm ci && npm run db:generate && npm run build -w @ledger/api`.
- Pre-deploy migration: `npm run db:migrate`. Start: `npm run start -w @ledger/api`. Health check: `/health`. Railway supplies `PORT`.
- Set `NODE_ENV=production`, `DATABASE_URL` from Railway PostgreSQL's private connection, a strong `SESSION_SECRET`, exact `FRONTEND_ORIGIN=https://app.dailyledger.store`, Google variables, `EMAIL_FROM`, and optionally `RESEND_API_KEY`.
- Add `api.dailyledger.store` to the API service, configure Railway's supplied DNS records, and wait for TLS before testing secure cookies. Express trusts one proxy hop. Cookies use `SameSite=Lax`, Secure in production, and no `Domain` attribute. Sibling HTTPS custom domains allow credentialed API requests without weakening cookie protection.
- Frontend and API may not share session secrets or database credentials. Migrations are committed. Never run `prisma db push` against production as a deployment shortcut.

### Preview and development authentication

Unrelated `vercel.app` and `railway.app` sites are not treated as sibling domains. For a preview use the same-origin `/backend` proxy (`NEXT_PUBLIC_API_URL=/backend`), point `API_INTERNAL_URL` at a dedicated staging API, and set that API's exact `FRONTEND_ORIGIN` and Google callback to `https://<preview-host>/backend/auth/google/callback`. Register each allowed callback explicitly. Use a separate staging DB/secret/OAuth client. Do not wildcard credentialed CORS, widen the cookie domain, or disable state/CSRF checks.

## Resend and durable cron

1. Verify a sending domain in Resend; publish its provided SPF/DKIM records.
2. Store `RESEND_API_KEY` and a verified `EMAIL_FROM` only on Railway API/worker services.
3. Create a second Railway service from the same repository with build `npm ci && npm run db:generate`, start `npm run worker`, and cron schedule `*/5 * * * *` (UTC).
4. Give the worker the same database URL, `SESSION_SECRET`, and frontend/email configuration. It processes bounded batches, closes connections, and exits.
5. Verify a task overdue by 24 hours, then completion/deletion/rescheduling, retry behavior, and opt-out with a staging account before enabling real deliveries.

Task mutations transactionally cancel stale jobs and enqueue a unique version/due-time key. The worker leases with `FOR UPDATE SKIP LOCKED`, recovers expired leases, persists attempts, creates unique in-app notifications, and rechecks ownership, version, completion, due time, plan allowance, and email preferences. Per-user locks serialize writes and email quotas. Retries back off and stop after five attempts. Resend receives a stable idempotency key; after its safe retry window expires, uncertain delivery requires operator review. Inspect `Job.lastError` and `DeliveryAttempt`; never blindly reset failed/uncertain jobs.

Recurring transaction schedules and completed repeating tasks are handled by the worker with unique occurrence keys; page loads cannot create duplicates. Financial monthly dates clamp to the last valid day of the next month. Task repeating timestamps currently preserve their UTC time across DST; see implementation limits below.

Announcements are created through the role-protected admin API with targeting, priority, publication/expiry, and versioned per-user dismiss/read state. Optional follow-up jobs recheck dismissals, targeting, expiry, product-update opt-in, and paid email quotas. Configure trusted administrators directly in the DB; there is no client role-upgrade endpoint.

## Plans and payments

`packages/shared/src/index.ts` centralizes initial prices and entitlements. The server serializes quota-check/write transactions using an owner row lock. Existing over-limit records remain readable/exportable and editable after downgrade; new/activation actions are restricted. Paid automation and recurring generation pause for Free accounts.

The payment provider is **not selected**. `/api/billing/checkout` is an explicit development stub enabled only by `BILLING_STUB_ENABLED=true` outside production. It never charges or activates entitlements. Production returns an unconfigured error. Before adding real checkout, select a provider, implement signature-verified webhook handling, unique provider event keys, server-verified entitlements, and idempotency tests. Client redirect state must never grant a paid plan.

## API reference

Every private route requires a Passport session. Mutations also require `Origin` matching `FRONTEND_ORIGIN` and `X-CSRF-Token` from `/auth/me`. JSON errors use `{error, details?}`; unauthenticated 401, forbidden 403, missing 404, stale/duplicate 409, validation 400.

| Endpoint | Behavior |
| --- | --- |
| `GET /health` | Liveness and non-secret configuration flags |
| `GET /auth/google` | Start state-protected Google sign-in |
| `GET /auth/google/callback` | Rotate session and redirect to frontend |
| `GET /auth/me` | Identity and per-session CSRF token |
| `GET /auth/csrf` | Pre-authentication CSRF token and session |
| `POST /auth/signup` | `{name,email,password,returnTo?}`; create email account and rotate session |
| `POST /auth/login` | `{email,password,returnTo?}`; authenticate existing account |
| `POST /auth/forgot-password` | `{email}`; durable reset delivery; generic result when configured |
| `POST /auth/reset-password` | `{id,token,password}`; consume valid reset and revoke sessions |
| `POST /auth/logout` | Invalidate PostgreSQL session and cookie |
| `GET /api/snapshot` | Owner's workspace, preferences, visible announcements |
| `GET /api/records?kind=task&q=...&page=1&limit=50&from=2026-09-01&to=2026-10-01` | Owner-scoped search, pagination (max 100), inclusive `from`, exclusive `to` |
| `POST /api/records` | `{kind,data}` validated against shared Zod schemas |
| `PATCH /api/records/:id` | `{kind,data,version}` with optimistic conflict detection |
| `DELETE /api/records/:id` | `{version}`; cancels pending jobs and removes habit/goal children |
| `PATCH /api/preferences` | Validated profile/timezone/currency/preferences |
| `GET /api/summary?month=2026-09` | Aggregates with period/currency metadata |
| `GET /api/reports/2026-09.csv` | Deterministic report CSV; Free current month, paid history |
| `GET /api/reports/2026-09.pdf` | On-demand streamed PDF; paid plan |
| `GET /api/export` | Owner's full JSON export |
| `POST /api/announcements/:id/dismiss` | `{version}`; versioned read/dismiss state |
| `POST /api/admin/announcements` | Admin-only shared announcement schema |
| `POST /api/billing/checkout` | `{plan}`; labeled stub, never grants entitlements |

All records use `{id,kind,data,version}`. Domain payload schemas live in shared contracts. Kind-specific data uses JSONB, with relational owner/date/status/unique occurrence indexes; amounts are validated integer minor units and serialized as bounded numbers without float conversion. Categories are explicit transaction strings; budgets are whole-month/currency budgets. No exchange-rate conversion is implied. UTC task timestamps are converted with the stored IANA timezone for due cohorts; other planning dates are local date-only values. The snapshot adapter currently loads all workspace records; list API pagination is available for growth.

## Current implementation limits

- No live deployments, Google secrets, Resend key, billing provider, or DNS are supplied. Email/password authentication was verified against a disposable local PostgreSQL database. External sign-in, paid billing, and real email must be staging-verified after configuration.
- Task recurrence preserves UTC time across daylight-saving transitions; a future wall-clock recurrence model should preserve an explicit local time and timezone. Manual due times are labeled in the device timezone.
- Meal plans use Monday–Sunday calendar weeks, including adjacent-month dates. Grocery list is ongoing and not restricted to the selected month. Goals are manual current values with separately tracked milestones; completing milestones does not silently recalculate progress.
- Current snapshot loading is appropriate for a personal MVP, but a large account should move feature screens to the paginated list API. No data retention limit is implied.
- Billing remains a non-activating adapter stub. Email follow-up read status is represented by the versioned dismiss state.
